# Weebie 💜  (run: npm install, then npm run dev)
Copy `.env.example` to `.env.local`, preserve any existing values, fill in the Firebase/Google public configuration, and restart `npm run dev`. Never put email-provider or OAuth secrets in a `NEXT_PUBLIC_` variable or browser code.
## Firebase
1. console.firebase.google.com: add a Web app and copy `apiKey`, `authDomain`, `projectId`, `storageBucket`, `messagingSenderId`, `appId`, and `measurementId` into the matching `NEXT_PUBLIC_FIREBASE_*` variables.
2. Authentication: enable Google + Email/Password
3. Create a Cloud Firestore database in production mode. Review `firestore.rules` against the intended Firebase project before publishing it; do not deploy rules to an unverified project or broaden permissions to fix a `permission-denied` error.
4. Realtime Database rules support the legacy room fallback and leadership trigger. Friend requests, private chat, room invitations, and global presence use Firestore and do not require `NEXT_PUBLIC_FIREBASE_DATABASE_URL`.
5. Friend, block, private-message, and room-invitation mutations use the authenticated Next.js Node API route at `/api/friends`; they do not require Cloud Functions. The host must run Next.js server routes and provide Firebase Admin credentials via Application Default Credentials or `FIREBASE_ADMIN_CREDENTIALS_JSON`. This repository does not configure a production Next.js host or establish its pricing; verify Node route support, server identity permissions, and costs with the chosen host before production use.
6. Room documents, membership, playback, room chat, and WebRTC signaling use Firestore. Room reads require Firebase Authentication; active room members can read shared room data, and only the room admin can change playback/source or moderate members.
7. Room leadership succession is maintained by Firestore Functions that reconcile active presence leases and the room's persistent `ownerUid`. After reviewing the target Firebase project and the function deployment's billing requirements, run `cd functions`, `npm install`, then from the project root deploy `firebase deploy --only firestore:rules,functions:reconcileRoomLeadership,functions:reconcileFirestoreRoomLeadershipOnMemberWrite,functions:reconcileFirestoreRoomLeadershipOnPresenceWrite`. Do not deploy without approval; no rules or functions were deployed as part of this change.

### Friends, presence, private chat, and room invitations
The existing Firestore data model is server-managed for relationships and invitations:

- `friendRequests/{sha256(senderUid, recipientUid)}` stores sender/recipient UIDs, sender display name/photo (and username when a verified token provides one), `status` (`pending`, `accepted`, `rejected`, or `blocked`), and timestamps. A recipient's live listener displays only pending requests.
- `users/{uid}/friends/{friendUid}` stores each side's accepted-friend record. `/api/friends` uses Firebase Admin transactions to create/repair both records, delete both records, and atomically apply blocks. Client writes to requests, friendships, and blocks are denied.
- `users/{uid}/presenceSessions/{sessionId}` holds a per-tab online lease (`uid`, `online`, `lastSeen`). Heartbeats refresh the lease; a friend is shown online only while at least one session is fresh (75 seconds). Logout/unmount removes the session where possible; a crashed/offline tab expires without a Cloud Function or scheduled cleanup. Multiple tabs/devices have independent session documents.
- `users/{uid}/rooms/{roomId}` is a private My Rooms index. Firestore only permits writing an index entry in the same atomic operation as that user's non-kicked `rooms/{roomId}/members/{uid}` membership record.
- `conversations/{sha256(sortedParticipantUids)}/messages/{messageId}` contains private message sender identity, text, and server timestamps. The API validates reciprocal accepted friendship and block state before opening/sending; Firestore rules independently restrict reads to the two current, unblocked participants and deny client writes.
- `roomInvitations/{sha256(senderUid, recipientUid, roomId)}` contains the verified inviter identity, recipient UID, room code/name, pending/accepted/declined status, and timestamps. The API validates accepted friendship, block state, active inviter room membership/session, room existence, and the recipient's kicked status. Invitation reads are limited to the two participants and client writes are denied. Room member presence leases are under `rooms/{roomId}/presenceSessions/{sessionId}`.

Global presence deliberately uses Firestore leases rather than introducing Realtime Database configuration: the repository's documented baseline does not supply a Realtime Database URL, and the existing Realtime Database path is a legacy room fallback. No new Firebase product, paid dependency, or Console setup is required for presence. Firestore usage is subject to the configured project's normal quotas and billing.

After confirming the correct Firebase project, the owner must publish the updated local `firestore.rules` for friend request reads, private `users/{uid}/friends` and `users/{uid}/blocks` data, owner/friend-scoped presence session reads, private conversation reads, participant-scoped room invitations, room-member presence sessions, and membership-checked My Rooms index writes. Client writes to friend relationships, blocks, private messages, and room invitations remain denied; their mutations use the verified-ID-token Node API. Publishing is intentionally not performed by this repository workflow.
## Real Authentication And Drive Setup
The app has no demo-account login. Email/password registration, Google sign-in/sign-up, password reset, profile display-name updates, and protected pages use Firebase Authentication. Google Drive uses a separate server-side OAuth authorization-code flow; its OAuth client secret and Drive refresh token never enter the browser.

1. In Firebase Console, create/open the project and add a Web app under Project settings > General. The supplied web config is already set in `.env.local`; Firebase web config values are public client identifiers, not server secrets. `NEXT_PUBLIC_FIREBASE_DATABASE_URL` was not part of the supplied config. If you use cross-device rooms, create a Realtime Database and set that URL separately.
2. In Firebase Console > Authentication > Sign-in method, enable Google and Email/Password. Set a support email for Google. Under Authentication > Settings > Authorized domains, make sure `localhost` and your production hostname are listed.
3. In Firebase Console > Build > Firestore Database, create the `(default)` database in production mode. From the project root, deploy the room security rules with `firebase deploy --only firestore` and deploy `cleanupDriveAuthorization` with `firebase deploy --only functions:cleanupDriveAuthorization`. The trigger deletes an encrypted Drive grant only after the last room using that creator's grant is deleted. The code stores rooms in `/rooms/{roomId}` with `/members`, `/messages`, `/signals`, and `/reports` subcollections.
4. In Google Cloud Console for the same Google Cloud project, enable **Google Drive API**. Google Picker API and a browser API key are no longer used by the Drive flow.
5. In Google Auth Platform > Branding/Audience, configure the consent screen and add your Google account as a test user while the app is in Testing. The server requests the read-only scope `https://www.googleapis.com/auth/drive.readonly`; public production use may require Google's OAuth verification for this scope.
6. In Google Cloud Console > APIs & Services > Credentials, use the existing **Web application OAuth Client ID** if suitable. Add `http://localhost:3000/api/drive/oauth/callback` as an Authorized redirect URI and the exact production callback URL before deployment. The existing Authorized JavaScript origin is not a substitute for this redirect URI.
7. Keep `NEXT_PUBLIC_GOOGLE_CLIENT_ID` and server-only `GOOGLE_CLIENT_SECRET` from the same Google Drive OAuth client. This is separate from Firebase Authentication's Google provider configuration. Set `GOOGLE_OAUTH_REDIRECT_URI` to the exact authorized callback URL (locally, `http://localhost:3000/api/drive/oauth/callback`) and set `DRIVE_TOKEN_ENCRYPTION_KEY` in the server environment or deployment secret manager. The encryption key must be a base64-encoded 32-byte random key; do not commit it or send it to the browser.
8. Configure Firebase Admin credentials for the Node server using Application Default Credentials (`GOOGLE_APPLICATION_CREDENTIALS` locally or the hosting platform's service identity) or the secret `FIREBASE_ADMIN_CREDENTIALS_JSON`. Firebase Admin must use the same project as `NEXT_PUBLIC_FIREBASE_PROJECT_ID` so the server can verify the web client's Firebase ID tokens; a conflicting `FIREBASE_ADMIN_PROJECT_ID` is rejected. The service identity needs access to verify Firebase users and administer the server-owned friend-request and friendship documents, as well as read room/member documents; the app stores only the AES-GCM-encrypted Drive refresh token in a server-only `driveAuthorizations` collection. No Firestore rules are loosened.
9. Preserve existing `.env.local` values, add the required server-only values, and restart the dev server. Sign into Weebie, connect Drive as the room creator, then select an MP4/WebM/Ogg video from the server-backed list. Other active room members use the protected stream endpoint and do not connect Drive or select the file.

If Drive is already shown as connected but the video picker cannot refresh authorization, check the Node server logs for `[drive-oauth] token refresh failed`. The log contains only a normalized error category and HTTP status, never a token or Google's raw error description. `invalid_client` or `unauthorized_client` means the server-side client ID/secret configuration needs checking; `invalid_grant` means the stored grant was removed and the host must reconnect; `temporary_failure` indicates a provider/network retry; `provider_error` is a non-retryable response that requires a new sanitized log entry to narrow down. Do not change Firebase Google Sign-In settings to troubleshoot the separate Drive OAuth client.

## Drive Streaming Test
1. Sign in to Weebie as the room creator, connect Google Drive, and create a Drive room with an MP4, WebM, or Ogg file that permits download.
2. Open the invite link in a second browser profile where a different user is signed in to Weebie. Join the room; do not connect Google Drive in that profile.
3. Press Play and seek forward/back. In the browser Network panel, the same-origin `/api/rooms/<room-code>/video` request should return `206` for ranged playback, with `Content-Range`, `Accept-Ranges: bytes`, `Content-Type`, and `Content-Length`. It must not redirect to a Google Drive URL.
4. In a private window or signed-out browser, request that stream endpoint and verify it returns `401`. A signed-in user with no active room membership must receive `403`.
5. Repeat with a camera-recorded MP4 selected from the host's Drive. It uses the same route; YouTube playback remains on its existing IFrame path.

## Independent Video Quality
Drive quality selection is local to each player tab and is not written to room playback state. Auto uses hls.js ABR (or native HLS where available); choosing a manual rendition pins that viewer to the exact generated HLS level. Only generated renditions that pass FFprobe dimension checks are shown. YouTube does not expose dependable manual rendition selection through its embedded player API.

Only the host can start preparation from the room controls. Preparation is never automatic: it downloads the entire selected Drive file to the server temporarily, probes codecs, dimensions, duration, audio and subtitle streams, creates lower-resolution HLS renditions, and removes the temporary source on success. Embedded subtitles are converted to protected WebVTT when possible; conversion failures are reported. Do not start preparation for a large Drive file until you have explicitly approved that processing.

The Node.js server requires FFmpeg and FFprobe on its PATH, or `FFMPEG_PATH` and `FFPROBE_PATH` pointing to executable binaries. Set `WEEBIE_MEDIA_DIR` to a private, writable, durable directory with enough free space for the source download and renditions. In production, this setting is mandatory; serverless or ephemeral filesystems are not suitable. The directory must be available to every app instance that may serve that room's HLS requests. Generated manifests, variants, segments, and subtitles are served only through same-origin endpoints that re-check Firebase session and active room membership on every request.

The repository's `firebase.json` configures Functions and database rules, but does not configure a Next.js hosting runtime or durable media volume. Production FFmpeg availability and storage therefore remain unverified; do not assume a Firebase Functions runtime can retain generated HLS files. Use an already available Node.js host with installed FFmpeg and a private persistent/shared volume, or keep quality preparation disabled until such a runtime exists. No external or paid service is configured by this project.

To test with two members, first configure and verify the Node.js media runtime, then use a small test video whose Drive download is permitted. The host explicitly prepares qualities; join from a separate browser profile as another active member. Choose different available manual levels in each player and confirm both continue at the same room timeline. Set one player to Auto, throttle only that browser's network in developer tools, and verify its displayed active level changes while the other player's choice stays fixed. Check Network requests for protected `/video/hls/` manifests and segments. This workflow has not been tested against a real Drive file, multiple browsers, or real network conditions in this environment.

Firebase web configuration is client-side, but `GOOGLE_CLIENT_SECRET`, `DRIVE_TOKEN_ENCRYPTION_KEY`, Firebase Admin credentials, and the encrypted Drive refresh token are server-only secrets. Do not prefix them with `NEXT_PUBLIC_`, commit them, or return them from an API route. A room stream is available only to a signed-in, active member; the server reads only the selected file ID from that room's source and streams byte ranges from Drive.

## Email Verification Links
Email/password accounts must verify their Firebase email before opening protected pages. Signup calls Firebase `sendEmailVerification`; the app applies `oobCode` links with Firebase `applyActionCode` and also supports Firebase's hosted action handler followed by a session refresh. Google sign-in remains exempt when Firebase reports the email as verified. No custom OTP backend or email provider is used.

1. In Firebase Console > Authentication > Sign-in method, enable Email/Password and Google.
2. In Authentication > Settings > Authorized domains, include `localhost` and the deployed site hostname.
3. In Authentication > Templates > Email address verification, review the sender and choose **Customize action URL**. To use this app's `applyActionCode()` handler, set that action URL to `https://<authorized-host>/verify-email`. Firebase appends `mode`, `oobCode`, `apiKey`, `continueUrl`, and `lang`; the app applies the action code and refreshes the signed-in user. This custom action URL is configured in the Firebase email template, while `sendEmailVerification()` supplies a same-origin continuation URL.
4. The email template has one custom action URL. For local custom-handler testing, temporarily set it to `http://localhost:3000/verify-email` and ensure `localhost` is in Authentication > Settings > Authorized domains; restore the deployed HTTPS URL before production. Alternatively, keep Firebase's hosted action handler, which applies the link and redirects to the generated `/verify-email` continuation; the app refreshes Firebase auth state there.
5. Copy `.env.example` to `.env.local` only if needed, preserving existing values. Test `/signup` with an email/password account, open the received link, confirm dashboard access, refresh, and check session persistence. Also test resend, expired/used links, protected room routes, and Google sign-in.

Email sending and action-code validation are handled by Firebase Authentication. No Resend API key, OTP hash secret, Cloud Function, or OAuth Client Secret is required for this flow.
## Local Emulator Testing
Local emulator mode is opt-in and uses the demo project ID `demo-weebie-local`; `.firebaserc`, `.env.local`, production Firestore rules, and normal `npm run dev` are unchanged. The emulator suite loads the existing `firestore.rules` and `database.rules.json` files.

Requirements: install JDK 11 or newer (JDK 21 recommended), select Node.js 20 to match `functions/package.json`, and have the Firebase CLI available. The first emulator start downloads emulator binaries.

1. In PowerShell at the project root, install project dependencies if needed: `npm.cmd install`, then `Push-Location functions; npm.cmd install; Pop-Location`.
2. In one terminal, run `npm.cmd run emulators`. The suite uses Auth `127.0.0.1:9099`, Realtime Database `127.0.0.1:9000`, Firestore `127.0.0.1:8080`, Functions `127.0.0.1:5001`, and the Emulator UI `127.0.0.1:4000`.
3. In a second terminal, run `npm.cmd run dev:emulator`, then open `http://localhost:3000`.
4. In Browser A, create an email/password test account and verify it using the link printed in the emulator terminal. In a separate browser or profile, repeat for User B. Emulator verification links are local; no email is sent.
5. Have User A create a room and User B join it. From the room member list, User A selects User B and chooses **Send Friend Request**. User B should see the request popup and badge without refreshing; accept or reject it and verify the updated friend/request state.
6. Use `http://127.0.0.1:4000` to inspect local Auth, Firestore, and Functions state. Stop the emulator terminal with Ctrl+C when finished.

Always use `npm.cmd run dev:emulator` only while the emulators are running. It opts the browser SDK and local server Admin SDK into the local endpoints and demo project. Normal `npm.cmd run dev` does not enable emulator connections. Do not run deploy commands for this workflow.

For local tunnel testing, `DEV_ALLOWED_ORIGINS` accepts a comma-separated list of extra development origins; it has no effect in production.

Room presence heartbeats and leaves are also reconciled by the authenticated Next.js room-presence API using a Firestore Admin transaction. This keeps `adminId` and member session pointers authoritative without requiring a deployed Cloud Function. Expired leases are reconciled when a room is listed or its live-room subscription reaches the lease deadline.

## Voice chat
Voice is opt-in and uses WebRTC audio only; no audio is uploaded or recorded. The default STUN server is `stun:stun.l.google.com:19302`. For restrictive networks, configure `NEXT_PUBLIC_TURN_URLS` (comma-separated), `NEXT_PUBLIC_TURN_USERNAME`, and `NEXT_PUBLIC_TURN_CREDENTIAL` with a TURN provider. TURN relays can incur provider and bandwidth costs.

## Playback limitations
YouTube playback uses the official IFrame API and follows browser autoplay, embedding, private-video, and owner restrictions. For Google Drive, only the room creator connects Drive and selects the video; active members watch through the authenticated, range-capable server stream. Google Drive download restrictions still apply, and the host must retain access to the file. Server streaming requires the OAuth client secret, redirect URI, encryption key, and Firebase Admin credentials described above. This project has no room-delete flow and Firestore rules disallow client-side room deletion; disconnecting Drive removes the host's encrypted refresh token, so any room using that authorization stops streaming until the host reconnects.
